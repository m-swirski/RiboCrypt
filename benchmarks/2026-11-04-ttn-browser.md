# TTN browser profile and multi-track smoothing, 2026-11-04

## Scope and reproduction

The reported production log had controller 0.17 s, bottom panel 0.31 s, track panel 2.55 s and final panel 0.09 s. The track timer contains both coverage extraction and track construction; it does not include network transfer and client rendering. Production browser URL, selected track(s), smoothing width, machine load, caches and browser rendering time were not supplied, so these measurements cannot reproduce or explain the production figure in isolation. This review does not establish a <1 s end-to-end latency on ribocrypt.org.

Measured on the processing server using the public `all_merged-Homo_sapiens` forward/reverse BigWigs and transcript `ENST00000589042` (363 exons; 109,224 spliced nt), R 4.5.3, ORFik 1.29.16, data.table 1.18.99. `OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1`, with data.table limited to one thread for controlled measurements. Filesystem caches were warm, in-process R and annotation startup is excluded. Other users/jobs share this machine. The profile benchmark is reproducible from this checkout:

```
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 Rscript benchmarks/ttn-browser-profiles.R
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 Rscript benchmarks/ttn-bigwig-exons.R
```

The exon benchmark compares different genomic intervals with the same total width; it isolates a useful difference in query shape, but does not prove the exact cost of exon count alone. The four-track benchmark uses the same actual BigWig repeatedly to control for data variance, not four independent real tracks. Timings are wall-clock and include normal run-to-run effects; do not generalize to a different server or cold caches.

## Results

- Warm `getProfileWrapper`, 1 track and k=9: original 0.222–0.239 s in three non-outlier trials; optimized 0.218–0.259 s. One original trial was 1.051 s. The optimization deliberately does not alter this single-track path.
- Four tracks, k=9: original 0.881, 0.902, 0.954, 0.963 s (median 0.928); optimized 0.661, 0.680, 0.688, 0.742 s (median 0.684), about 26% faster. Exact profile equality was checked for every row and column. The improvement avoids repeating identical ORFik leader/trailer extensions within one request; distinct k-mers still get their own extension, and caches do not cross sessions or requests.
- With k=1 (no extension), warm TTN BigWig `coveragePerTiling` was 0.088–0.134 s. A synthetic 363-interval query with the same total width took 0.086–0.095 s; one contiguous 109,224 nt interval took 0.045–0.047 s in four warm trials, with 0.093 and 0.794 s outliers. Many exons add noticeable query overhead, but do not explain a 2.55 s track panel by themselves on this machine.
- For TTN minus-strand BigWig output, replacing the current `rev`/`relist` sequence with an equivalent vector-indexing experiment took about 0.002 s versus 0.005 s. This small absolute gain does not justify a C++ rewrite or an upstream behavioral change without broader profiling. An attempted direct GRanges extension was ~0.045 s versus ~0.086 s, but changed metadata/names and was rejected; its genomic boundaries and circular behavior also need validation.
- On an eight-call k=9 R sampling profile, ORFik `coveragePerTiling`/BigWig path accounted for roughly 59% and the two ORFik extension calls ~23% inclusive; these are profiler samples, not a controlled decomposition, and calls overlap. Plot construction using an already built area template was approximately 0.03–0.05 s warm aside from a 0.57 s outlier. Plotly-building a single track was 0.044 s and serializing its four traces about 0.077 s, ~1.57 MB JSON in that test; the full browser widget and actual user download/render were not measured. GC and shared-server contention can create long-tail latency. In particular, R's `system.time()` can trigger GC before its measured expression, making whole-process profiles misleading if its call is included inside the sampling profile.

## Change and safety

`build_browser_profiles()` now precomputes repeated non-unit smoothing extensions once per request and passes the original GRangesList to the same existing profile functions. No downsampling, BigWig replacement, cross-session caching, coverage/count modification, rendering change or ORFik package installation is involved. The unoptimized path remains for a single track and unique smoothing widths. `tests/testthat/test_browser_shared_smoothing.R` compares complete frame and non-frame profiles, different log settings, and serial/multicore execution; the existing browser suite is also exercised. The `benchmarks/ttn-browser-profiles.R` real TTN comparison checks exact equality for one and four tracks.

Set `options(RiboCrypt.browser_profile = TRUE)` in the app process to get separate `[browser profile]` timings for track controls, coverage profiles, track plot construction, subplot assembly, and y-axis/zoom configuration. It defaults to FALSE. Preserve the existing top-level timers when comparing and record precise experiment, transcript, genome/transcript view, selected track count, k-mer and frame display; measure multiple warm and cold requests. Capture browser receive-to-visible time, transfer bytes, browser/Plotly version, server GC/CPU/memory pressure, and server package/commit versions. The public deployment is not changed by a checkout edit; test a separate dev app before an intentional deployment.

## Next targets and C++ decision

1. Measure the production configuration with phase logging and browser instrumentation. If coverage is dominant, compare BigWig interval import and ORFik range extension separately on the deployed storage, including negative and positive strands, genomic and transcript views, many tracks, and cold caches.
2. TTN's full-resolution traces produce sizable Plotly payloads. If browser transfer or SVG rendering dominates, investigate zoom-aware display aggregation or alternative rendering, retaining complete data for hover/zoom/download and validating visual and coordinate equivalence. This is a product behavior change and needs tests across frames, guide lines, zoom, selection, and export; a server-only R/C++ speedup cannot fix client rendering.
3. If repeated safe extension calls dominate real multi-track sessions, consider a tested ORFik API that extends both ends once while preserving all names, metadata, exon order, boundaries and circular cases. Profile first. ORFik BigWig import already calls native code and the isolated R reversal cost here is only milliseconds; C++ is not warranted for it yet.
4. If GC or server contention dominates tail latency, measure allocations and concurrency under representative loads instead of setting a global thread count or silently reusing mutable per-user data. Any cache must be session-safe and invalidated by range, file identity/modification, view, smoothing and frame settings.

## BigWig exon reader investigation

The installed rtracklayer 1.70.1 `BigWigFile` import method converts all requested ranges and invokes `BWGFile_query` once. It does **not** perform one R-to-C call or reopen the file per exon. In the [rtracklayer C source](https://github.com/bioc/rtracklayer/blob/devel/src/bigWig.c), `BWGFile_query` opens the file once and calls UCSC `bigWigIntervalQuery` inside a loop over ranges; it returns per-range numeric arrays. The linked source is the public development version; confirm the source for any deployed package version before relying on its details. ORFik subsequently reverses each minus-strand exon and concatenates it in the imported order. Any replacement must preserve those exact semantics, missing data/zero behavior, overlapping or duplicated exons, sequence naming, integer/floating values and failure modes. `rtracklayer` is itself native code, so simply wrapping its existing loop in C will not remove per-exon indexed queries.

A local prototype groups exon intervals separated by at most 500 bases, asks the existing native rtracklayer reader for those spans, then extracts each original exon in transcript order. The general technique is also used by [SignalFrame](https://github.com/clarkvd/SignalFrame), although SignalFrame focuses on interval summaries and is not established here as a drop-in per-base, transcript-oriented reader. [UCSC's BigWig streamer](https://github.com/ucscGenomeBrowser/kent/blob/master/src/lib/annoStreamBigWig.c) queries contiguous spans, while [bigwig-loader](https://pmc.ncbi.nlm.nih.gov/articles/PMC10782802/) targets batched multi-track GPU workloads, a different regime from one interactive transcript. [libBigWig](https://github.com/dpryan79/libBigWig) provides native interval access and block iterators; this server does not currently expose its development headers/library, and a new dependency or vendored implementation would require portability and licensing review.

`benchmarks/ttn-coalesced-prototype.R` runs an alternating warm comparison. On TTN (minus, 363 exons, 109,224 bases), coalescing reduced native queries from 363 to 97 and read 153,511 instead of 109,224 bases. Across six alternating trials the original reader took 0.091, 0.097, 0.097, 0.098, 0.139 and 0.863 s; the prototype 0.076, 0.076, 0.076, 0.081, 0.086 and 0.086 s. Every resulting coverage, gene, position and frame column was identical. The large 0.863 s observation is a tail outlier, not assumed to be an algorithmic speedup. On a separate plus-strand high-exon transcript ENST00000454784 (173 exons, 24,669 bases), results again matched, but the prototype was 0.055–0.067 s versus a typical 0.047–0.053 s original: a small regression. These are two real examples, not proof of broad correctness or performance. The 500-base threshold was explored, not optimized on an independent test set.

Conclusion: nearby-exon coalescing is promising for unusually exon-dense transcripts, but the current data do not justify shipping a general native reader or adding a BigWig C dependency. The absolute warm TTN gain in paired typical trials is on the order of tens of milliseconds, much smaller than the multi-second report. A production proposal needs a larger held-out set, both strands, genomic/transcript modes, different BigWigs, remote and cold I/O if used, peak memory/overfetch caps, empty/overlapping/duplicated intervals, missing chromosomes, and exact output/exception comparisons. A native reader that actually merges compressed-block reads and scatters them into a final vector could reduce allocations and repeated decompression, but must show material end-to-end gains, support existing build platforms, and be independently reviewed before replacing the established reader.

Eight alternating warm trials, including equivalent R output table construction: TTN original median **0.148 s**, libBigWig per-exon **0.064 s**, libBigWig with gap 500 **0.045 s**. The 173-exon plus-strand transcript original median **0.092 s**, gap-500 **0.016 s**. A 500,000-base gap merging the whole TTN span was slower (0.245 s), showing overfetch matters. All output columns matched exactly for these two real transcripts, and 20 synthetic integer/fractional, positive/negative-strand, empty-signal, overlapping and duplicate interval tests passed. These are local warm-cache trials on two files, not comprehensive production validation. The prototype currently treats a NULL libBigWig result as zero coverage even though its API also uses NULL for an I/O error; it lacks production-grade error propagation, remote-I/O verification, length/budget guards, portable dependency packaging and broader species/coordinate tests. **Do not install or use it as an ORFik replacement.** A tested and safely packaged native integration is a worthwhile next iteration, but the full browser also needs attention.

`ttn-browser-complete-profile.R` exercises actual TTN annotation, app-style templates, one RFP track and full widget generation on this server, excluding Shiny/network and client draw. In three initial trials bottom + track + subplot took **2.455, 2.533 and 0.888 s**; R phase logs identify coverage **0.395–0.587 s** and track construction **0.024–1.206 s**, with first-run and contention/GC effects. An R sampling profile of six complete runs (including Plotly JSON creation) attributed 22.6% of samples to GC; inclusive categories overlap, so they are not additive. `plotly::plotly_json` for the plot portion took **0.199–0.491 s** and was **3.46 MB**, excluding the onRender hook payload. These measurements explain why BigWig alone cannot achieve the requested full user-visible second.

A real standalone TTN Plotly widget was rendered with Chromium 156 in headless software mode using Playwright, 1400×900; it is not a live Shiny request or a measurement on a user's GPU. Three alternating before/after trials per display mode give median `newPlot` draw / local document-load time in seconds:

| Mode | Before draw / load | Compact payload draw / load |
|---|---:|---:|
| lines | 1.618 / 2.553 | 1.687 / 2.565 |
| columns | 2.520 / 3.483 | 2.552 / 3.384 |
| area | 1.745 / 2.820 | 1.761 / 2.703 |

Individual timings varied substantially. The compact payload is primarily a network/serialization/allocation improvement; these data do **not** demonstrate a reliable speedup in Plotly drawing itself. Lines and area are SVG scatter traces. Columns uses three WebGL scattergl traces for detailed view plus SVG overview traces. An experimental area-to-WebGL mutation created actual scattergl traces and returned from `newPlot` in ~1.37–1.63 s, but generated subsequent 9–11 s long tasks with software rendering; do not enable by default on this evidence. Hardware GPU, browser support, export fidelity, hover and zoom need separate evaluation. Plotly documents [scattergl fill](https://plotly.com/python/reference/scattergl/) and warns that [WebGL and SVG traces are not complete substitutes](https://plotly.com/python/performance/).

A separate **non-production** min/max envelope experiment reduced the three area traces from 36,408 points each to ~4,250 each and gave ~1.15 s median initial draw in four software-rendered runs; it omitted full-resolution zoom restoration, original-point hover, accurate local y-range and export guarantees. It is evidence for a future viewport-aware representation, not a drop-in change. The bottom annotation/sequence tracks contain thousands of additional SVG points; reducing coverage alone cannot eliminate their rendering cost. Full-resolution data must remain available, and features such as dynamic zoom, frame selection, hover, selection and exports require explicit tests before an adaptive path ships.

### Implemented sequence payload optimization and copy correction

Previously, the onRender hook sent six full x/y/text arrays for every nucleotide and amino-acid frame, despite only displaying letters when zoomed. It now sends the original full nucleotide string, three translated strings and small trace descriptors, reconstructing the visible letters client-side. TTN `fetch_JS_seq` JSON went from **3,200,653 to 219,227 bytes**. In an alternating eight-trial benchmark of the full HTML-widget serializer, the widget went from **8,392,089 to 3,699,566 bytes**, and median serialization from **0.420 to 0.181 s**; one old trial was 1.516 s. Reproduce with `git show 3c72c86:R/js_helpers.R > /tmp/ribocrypt_old_js_helpers.R`, then `Rscript benchmarks/ttn-widget-serialization.R` (3c72c86 is the baseline revision). These measurements exclude transport/compression and real Shiny/browser rendering.

Browser tests compare the six actual old/new zoomed sequence traces for lines, columns and area, including x/y/text; Node tests cover all reading frames, both AA letter styles and ambiguous nucleotides. During copy validation we found the existing click handler dropped the first visible base because a 1-based plot coordinate was used as a zero-based string index. It now copies the inclusive integer positions in the visible range, including reversed and fractional ranges. Real headless browser tests verify both clipboard and Shiny input: TTN full view **109,224 bases** and 40,000–40,100 **101 bases**; previous results were 109,223 and 100. This corrects copy behavior intentionally. `benchmarks/ttn-sequence-render-equality.cjs` and `ttn-sequence-copy-equality.cjs` require saved old/new local widgets and the temporary Playwright setup; unit tests do not.

Raw timing, profile and validation logs for these experiments are retained in `benchmarks/results/2026-11-04-ttn/`. Headless client artifacts are generated from local standalone widgets; they do not represent an interactive connection to the production service.
