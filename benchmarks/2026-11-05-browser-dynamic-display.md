# Dynamic browser rendering

The standard browser and Observatory share Dynamic and User-defined controls. Dynamic uses the visible inclusive nucleotide span: up to 500 nt columns with k=1, 501–10,000 area with k=9, and over 10,000 lines with k=9. Plotly zoom events notify the server only when the category changes; the interval is restored after rendering. Coverage is recalculated when k changes. Existing Plotly templates for lines, area, columns and the cached gene/sequence annotation panel are reused. Existing links with explicit frame/k-mer settings and no mode restore as User-defined.

Run `benchmarks/browser-dynamic-smoke.cjs` against the isolated app to exercise real zoom transitions. Exact threshold, cache context and URL behavior are also tested in `test_browser_dynamic_display.R`. Timings depend on the selected transcript, tracks, data storage and browser; zoom that crosses a category boundary requires a server round trip and plot update.

Real-data smoke test: ATF4 ENST00000674920 in the standard browser and Observatory. Both changed area → columns → area, kept the requested x range, and reported no JavaScript errors; Observatory aggregated 4,522 runs. In that shared-server observation, its controller took about 0.7–1.0 s and track/subplot preparation about 0.06–0.59 s per transition; these are server log timings, not a controlled end-to-end benchmark. A legacy URL specifying lines and k=3 restored User-defined mode.

## Client-side switching iteration

For frame-split Ribo-seq tracks without a summary track, the initial request prepares both k=1 and k=9 profiles. A padded BigWig read supplies both for the normal browser; Observatory reads its collection once and builds both from the same aggregated profile. The browser changes trace data locally with one Plotly update, keeping one neighbouring point beyond each viewport boundary. Raw data remain available for detailed columns and downloads. The existing server-driven path remains for mixed/unframed tracks and summary-track mode; User-defined mode is unchanged. Copy/sequence hooks and frame legend behavior are retained.

A real ATF4 comparison gave identical frame x/y values to the previous server-driven implementation for initial area and zoomed columns. Independent TTN checks matched k=1 and k=9 positions, frame labels and counts exactly, including log scale and frame subsets (`browser-dynamic-ttn-dual-verify.R`). Initial TTN server track/subplot work in one warm run was 1.63 s (coverage 0.39 s, track construction 1.14 s); the Plotly trace JSON was 1.97 MB and the client hooks 1.16 MB. These figures exclude the annotation panel and browser draw, and are single shared-server observations, not guarantees. Retaining both profiles increases initial payload and memory.

In headless software Chromium on the shared server, a TTN run took 4.58 s from Generate to the initial line view, 1.93 s from a programmatic zoom to the area switch, and 1.32 s to columns. The Plotly zoom call itself took 1.32 s and 0.62 s respectively, before the client mode update completed. These figures include browser rendering and differ from actual GPU/network performance. The previous client test before the single-update change took 2.26 s and 1.35 s in another run; these uncontrolled observations do not establish a precise speedup. Full-resolution TTN SVG rendering remains a bottleneck. Test scripts: `browser-dynamic-client-smoke.cjs`, `browser-dynamic-ttn-smoke.cjs`, `browser-dynamic-equivalence.cjs` and `browser-dynamic-ttn-backend.R`.
